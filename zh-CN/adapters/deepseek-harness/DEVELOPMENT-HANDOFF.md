# GitLearnOS × DeepSeek Harness 开发交接卡

[English](../../../adapters/deepseek-harness/DEVELOPMENT-HANDOFF.md)

## 使命

接手 GitLearnOS 在官方 DeepSeek Harness 上的下一阶段开发。

不要把这张卡、当前适配器或已有路线图当成功能规格。完整研究两个系统，实际使用
正在运行的产品，自行识别最有价值的机会与弱点，并作出最能推进学习产品目标的
开发判断。

## 产品意图

GitLearnOS 应让一个有能力的主 Agent 更擅长发现、整理、复习并利用真实学习证据，
同时让长期状态始终由学习者掌控。应发挥 DeepSeek Harness 的原生优势，而不是
只把提示词复制进去，或复刻另一个 Agent 环境。

结果应当原生、实用且有辨识度。只有真正改善学习闭环、降低学习者负担，或让系统
更加诚实、可观察、可靠时，技术创新才有价值。

## 权限

你可以在这个公开模板内自主研究、设计、实现、重构、测试和编写文档。根据证据
自行决定范围与顺序。当子代理或 Harness 自身扩展面能带来真实价值时，可以使用。

不要等待预先列好的功能清单。只有当某项决定需要新增授权、会暴露私密数据、会
改变发布或可见性、会产生异常的外部成本，或者无法通过仓库与官方文档解决时，
才询问维护者。

## 不可破坏的原则

- 修改前完整阅读 `AGENTS.md` 与 `GITLEARNOS.md`。
- 学习者 Git 仓库始终是正式、可检查的学习事实来源。
- 学习决策由唯一主 Agent 负责；助手、检索、工作流和 UI 不得成为竞争权威。
- 先解决学习者眼前需要，再处理仓库管理。
- 明确区分证据、解释、掌握状态和外部系统状态。
- 没有直接证据，不得声称写入、提交、检索、摄入、定时运行、交付或学习结果。
- 保留部署问询门槛、有效写入权限、隐私边界、可撤销 Git 行为、模态限制与诚实
  自动化语义。
- 不得削弱 Harness 安全机制，也不得把 `safe-auto` 变成无限制批准。
- 不得把学习者资料、凭据或私密状态发送给未经批准的服务。开发和评测使用合成
  fixture。
- 保留无关工作。英文是正式版本；同步维护要求提供的中文阅读版本。

## 工作方式

从当前实际 checkout 与安装状态出发，不从假设出发。检查官方 Harness 版本、
生命周期与扩展契约、现有 GitLearnOS 适配器、评测证据和已知失败。容易变化的
行为必须以官方上游来源为准。

自行开发前，主动调研 GitHub 上现有的 DeepSeek Harness 生态。对于相关且仍在
维护的插件、Bundle、工具、示例、基础设施及相邻开源项目，只要能带来更好的结果，
就可以合理复用、组合、适配，或通过上游贡献加以改进。生态发现本身也是工程工作：
必须针对已安装的 Harness 版本验证兼容性，并检查源码、许可证、维护状态、安全与
数据边界、依赖和安装成本、与 GitLearnOS 的重叠以及真实运行表现。对集成项固定
版本、保留署名，并测试组合后的完整系统。受欢迎或表面上适合本身不构成充分证据，
任何集成都不得削弱本卡片中的不可破坏原则。

自行形成产品假设，并用真实的学习者行为检验它，包括用户没有点名 GitLearnOS，
以及 Agent 应判断完全不需要执行 GitLearnOS 操作的情况。优先选择能够证明假设的
最小完整产品增量，但不能把薄包装、纯提示词修改、模拟成功或文档承诺当作原生开发。

把失败当作产品证据。只修复证据支持的问题，重跑相关评测；未解决的限制应明确
保留，不能为了得到通过标签而优化报告。

## 有效交回的定义

只有形成可审查实现并完成与风险相称的验证后，才交回工作。交回必须说明：

- 你作出的产品判断及其原因；
- 实际改动、准确路径与版本边界；
- 哪些内容在真实 Harness 中运行过，而不只是 mock；
- 可观察证据，包括失败与未变化状态检查；
- 安全、隐私、成本与兼容性影响；
- 仍然未知或主动延期的部分；
- commit、发布状态、回滚边界与下一个需要判断的问题。

不得凭总体印象报告“完全适配”“原生”“已安装”或“通过”。每项说法都必须绑定
明确范围与可复现证据。

## 起始证据

仓库、Git 历史、已安装 Harness profile 和现有评测产物只是起始证据，不是关于
应该开发什么的指令。依赖它们之前先验证是否仍然最新。
